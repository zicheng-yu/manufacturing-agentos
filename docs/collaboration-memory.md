# 跨部门关联与记忆核查（YOU-130）

## 交互的实际边界

平台目前通过事件、信号、领域规则和经营决策助手汇总跨部门关联，并非多个模型已经自主协商、审批或执行。两条演示数据主线继续使用现有上卷机制，不新增通用编排引擎。

简报在原三项决策表后增加「跨部门关联证据」，列出关联对象、类型、部门、信号编号、原始事件编号与标题。共同物料、共同供应商、共同原因标签分开建键，避免物料编码恰好与供应商名称相同时误关联；supplier / supplierName 别名可正确对应。人员影响从HR事件的部门字段读取，不依赖信号标题猜部门。

共同实体表示值得联合核查，共同原因标签表示标签共现，人员风险表示可能影响处置能力；均不直接证明因果。模型提示词也不再要求把这些关联解释成已经确定的相互放大关系。

## 本轮修复的记忆与来源问题

1. 记忆按领域、类型、来源、智能体与本轮问答去重。不同对话会保留各自的事实来源，删除一轮不会让其他对话的相同事实消失。
2. 记忆去重保留标点，1.2与12不再被合并。fact / pending / suggestion即使内容相同也保持类型。给模型的同一对话工作记忆可合并完全相同的重复项，保留最新时间与来源。
3. 提示词将记忆标为历史记录，包含时间、来源轮次和类型；本轮业务数据优先，待核与建议不会被统称为「已确认信息」。仍只读取本对话最近6轮的工作记忆，不把其他对话的旧数字灌入本轮。
4. 结构化事实和自动待办只来自业务分析或核验过的context。模型新提的事实进入待核线索，行动进入建议，不因业务分析为空就自动升级为事实/执行任务。模型正文仍需要人工核验，这不是对所有自由文本语义的形式化保证。
5. 相同开放待办仍在领域内去重，通过task_turn_sources保留引用轮次；删除原创建轮时，把来源移交给仍引用它的轮次。合并的事件也按其他问答实际记录的eventIds转移归属，最后一个来源删除时再按原删除语义清理。历史任务来源在启动迁移时补齐，未改变任务状态或重新执行动作。

## 验证

`test/collaboration.test.ts` 覆盖两个独立对话的重复事实与删除、共享任务/事件引用、数值与类型区分、模型空分析边界、历史信息标签、字段碰撞防误关联、供应商别名与官方主线证据追溯。原demo与官方主线测试均须通过。

改动涉及core/memory、智能体运行时和提示词、数据库的任务来源关联表、executive简报；它们是本问题实际发生的位置。没有修改领域业务表或全局界面，没有接入新的模型服务，也没有向队友发送消息或自动批准业务动作。
